# Razer Axon 2.9.1.0 — вход в учётную запись и зависимость от сети

Автор работ: Wehrwolfmann. Начато 2026-08-12.

Продолжение `установка_под_wine_2_9_1_0.md`: там доказано, что **установка** 2.9.1.0
проходит на голом префиксе wine-11.15. Здесь разбирается то, что происходит **после**
установки — вход в учётную запись Razer и сеть.

Замерный префикс: `~/.wine-axon-auth` (отдельный, создан с нуля 2026-08-12).
Wine: системный **wine-11.15**.

---

## TL;DR

1. **Своего входа у Axon нет.** Приложение не показывает ни формы логина, ни кнопки
   «войти». Учётные данные оно спрашивает у **отдельной службы Razer Central**
   (модуль `Natasha` из манифеста) по локальному named pipe. Web-интерфейс Axon умеет
   только *выйти* (`logout`), после чего окно входа рисует опять же Razer Central.
2. **Токен — не OAuth.** В веб-бандле нет ни `client_id`, ни `redirect_uri`, ни
   `code_challenge`, ни `Bearer`. Хост отдаёт странице готовый JWT, страница меняет
   его на серверную сессию через `POST /v1/login`, и дальше подписывает запросы
   непрозрачной строкой в заголовке `Authorization`.
3. **Первая точка отказа под Wine — не сеть, а отсутствие Razer Central.** Замер: свежий
   префикс, Axon установлен, Razer Central нет → приложение доходит до
   `Program.cs:TryLoginAsync / Start userLogin` и **зависает навсегда**, не открыв ни
   одного окна и не сделав **ни одного сетевого соединения** (проверено `ss`).
4. Установка Razer Central под Wine требует **настоящего .NET Framework 4.8**
   (`winetricks dotnet48`), потому что wine-mono его проверку не проходит. С ним
   Razer Central 7.23.0.1220 ставится и служба `RzActionSvc` работает.
5. **Вторая (и последняя) точка отказа — песочница Chromium.** Окно входа Razer ID
   рисует CefSharp внутри Razer Central; под Wine рендерер не стартует вовсе
   (`--type=renderer` в списке процессов отсутствует), и окно белое. Лечится флагом
   **`--no-sandbox`**.
6. ⭐ **С этими двумя правками вход под Wine работает целиком.** Гостевой вход пройден
   живьём: окно Razer ID → выдача учётки → перезапуск Axon с `-showui` → WebView2 →
   витрина. Снимки в `~/Изображения/Screenshots/axon-2910-окно-входа-razer-central.png`
   и `axon-2910-главное-окно-гость.png`.
7. **Офлайн приложение бесполезно.** Установка без сети «проходит», но молча остаётся
   без WebView2; вход без сети невозможен ни на первом заходе, ни на последующих.

## 1. Как устроен вход

### 1.1. Три слоя и кто за что отвечает

```
┌──────────────────────────────────────────────────────────────┐
│ RazerAxon.exe (.NET 8, WinForms-оболочка)                     │
│   └── RazerAxon.UserManager.dll                               │
│         ├── AccountManagerClient ──┐                          │
│         └── UpdateClient ──────────┤ named pipe               │
│                                    ▼                          │
│ RazerCentralService.exe (модуль Natasha 7.23.0.1220)          │
│   ├── AccountManager  — вход, токен, профиль, облачные настройки│
│   ├── UpdateManager   — обновления                             │
│   └── NAC (GUI)       — ОКНО ВХОДА Razer ID                    │
│                                                              │
│ WebView2 (msedgewebview2.exe)                                │
│   └── SPA с https://axon-api.razer.com/2.9.1.0/              │
│         общается с хостом через chrome.webview.hostObjects.*  │
└──────────────────────────────────────────────────────────────┘
```

Разделение обязанностей жёсткое:

| Слой | Что делает при входе |
|---|---|
| `RazerAxon.exe` | при старте зовёт `TryLoginAsync`; сам форму входа **не рисует** |
| Razer Central | держит учётку, показывает окно Razer ID, отдаёт JWT по IPC |
| WebView2/SPA | получает готовый JWT от хоста и меняет его на сессию API |

### 1.2. Что делает нативная часть

Настройки окна лежат прямо в `appsettings.json` установленного Axon:

```json
{
  "WebWindowStartupSettings": {
    "StartupUri": "https://axon-api.razer.com/2.9.1.0/",
    "Width": 1280, "Height": 720,
    "WebServiceDomain": "https://axon-api.razer.com/v1"
  }
}
```

⭐ Важная поправка к прежним заметкам: **origin витрины — `axon-api.razer.com`,
а не `axon.razer.com`.** В бандле `REQUEST_URL` пуст во всех четырёх окружениях
(`dev/test/pro/staging`), то есть все запросы идут **same-origin** — туда, откуда
загрузилась страница. Строка `axon.razer.com` в бандле встречается только в ссылках,
которые открываются во внешнем браузере (`/faq/`, `/communityRules/` и подобные).

### 1.3. Что делает веб-часть (разбор бандла `axon.b454555f59e3550b4628.js`)

Бутстрап:

```js
window.SequoiaClientObj.getUser();          // → {code:0, data:{Token, IsGuest, Id}}
window.SequoiaInfo.is_guest = a.data.IsGuest;
window.SequoiaInfo.token    = a.data.Token;
window.SequoiaInfo.uuid     = a.data.Id;
window.SequoiaClientObj.getPcUniqueCode().then(...)   // → SequoiaInfo.pcCode
return login({token: a.data.Token, is_guest: ..., uuid: a.data.Id});
```

Обмен токена на сессию и подпись запросов:

```js
post(`${REQUEST_URL}/v1/login`, {token, is_guest, uuid})
  → window.SequoiaInfo.authorization = data.authorization
  → window.SequoiaInfo.country       = data.country

axios.defaults.withCredentials = true;
axios.create({headers: {"X-Requested-With": "XMLHttpRequest", "X-Version": "2.9.1.0"}})
  .interceptors.request.use(cfg => {
      cfg.headers["Authorization"] = window.SequoiaInfo?.authorization || "";
      cfg.headers["X-Language"]    = window.language || "en";
  });
```

Особенности, которые стоит знать при пересборке клиента:

* Заголовок `Authorization` — **непрозрачная строка** из ответа `/v1/login`, не
  `Bearer`-JWT (префикса нет). `withCredentials: true` → cookie тоже уходят.
* Просроченную сессию сервер помечает **`403`, а не `401`**; обработчика `401` в
  бандле нет вообще. На `403` (кроме самого `/login`) клиент молча повторяет
  `/v1/login` с тем же JWT.
* `code == 1001` в теле ответа → до трёх `location.reload()`; счётчики
  `refreshNum`/`reloadNum` живут в `localStorage`.
* HTTP `503` → событие `SERVER_ERROR_503`, `502` → `server_maintain`.

⭐ **Кнопки «войти» в веб-части не существует.** Все три места, которые выглядят как
вход (`UC_LOGIN`, экран онбординга, модалка гостя), вызывают **`logout()`**:

```js
case "UC_LOGIN":  window.SequoiaClientObj.logout(); break;
case "UC_LOGOUT": window.SequoiaClientObj.logout(); break;
```

Смысл такой: страница всегда работает под уже выданной учёткой (гостевой или полной).
«Войти» = сбросить текущую (гостевую) и дать нативному хосту показать окно Razer ID.
`OpenLoginWindow` в бандле используется **только для Spotify**, не для Razer ID.

Гостевой режим — полноценный: `window.SequoiaInfo.is_guest` гасит избранное,
плейлисты, публикацию, голосование и пополнение, но каталог показывает.

### 1.4. Где хранится токен

Канонический путь (оригинальное приложение) — внутри Razer Central: учётка
сериализуется как XML `RazerUser` (см. `razer-central-ipc.md`), в нём `<Token>` (JWT),
`<LoginId>`, `<AccessToken>`, `<AccessTokenExpirationDate>`, `<IsGuest>`. Axon его
только запрашивает и в реестр/файл сам не пишет.

Команды AccountManager, которыми это делается (service type 4):

| Команда | ID | Смысл |
|---|---|---|
| `TryLogin` | 44 | автологин при старте — то, что зовёт `TryLoginAsync` |
| `GetCurrentUser` | 3 | получить `RazerUser` (там же JWT) |
| `RefreshToken` | 4 | продлить |
| `StartLogin` | 1 | показать окно входа |
| `TryAutoLoginAsGuest` | 61 | гостевой автологин |
| `WebApp_SetLoginSuccessFromWeb` | 131094 | **втолкнуть готовый JWT снаружи** |

Последняя команда — та самая дверь, через которую порт вставляет токен, полученный
своим окном входа (`razer-token-inject.py`).

В **порте** токен лежит файлом:

```
~/.config/razer-axon/token.json
(и копия в префиксе: drive_c/users/<user>/AppData/Local/Razer/RazerAxon/wine_login_token.json)
```

Формат — ровно `WebAppTokenInfo`, который ждёт команда 131094:

```json
{"convertFromGuest": false, "token": "eyJhbGciOiJFUzI1NiI…", "isOnline": true,
 "isGuest": false, "uuid": "RZR_…", "loginId": "user@example.com",
 "tokenExpiry": "2026-04-08T21:33:05.000Z", "stayLoggedIn": true}
```

### 1.5. Единственный настоящий OAuth в Axon — и он НЕ для входа

В веб-бандле OAuth нет вообще. Но в нативной части он есть — в
`RazerAxon.UserManager.dll` (строки достаём `strings -el` из установленного файла):

```
Failed to retrieve SSO token: No logged-in user.
grant_type
razer_jwt_bearer
redirect_uri
https://oauth2.razer.com/services/code_sso
Authorization
Bearer
code
…
GetSsoCodeAsync failed. result is empty
GetZVaultWebUrl
https://razerid.razer.com/token-login?c=
Open user ZVault web with sso code failed.
```

Читается однозначно: имея **уже полученный** JWT, приложение делает
`POST https://oauth2.razer.com/services/code_sso` с
`grant_type=razer_jwt_bearer`, `redirect_uri=…` и заголовком `Authorization: Bearer <JWT>`,
получает одноразовый `code` и открывает `https://razerid.razer.com/token-login?c=<code>`.

То есть это **не вход, а «доставка уже существующей сессии в браузерное окно»** —
чтобы страницы профиля, смены пароля и zVault (`https://gold.razer.com`) открывались
сразу авторизованными. Источник JWT остаётся прежним — Razer Central.

### 1.6. Как именно Axon зовёт вход (по строкам того же DLL)

```
Razer\Razer Services\Razer Central\Razer Central.exe
App not installed  /  Service not found  /  Service is
Call AccountManagerClient.StartLogin failed.
Wait login failed.
Login over time:
Get current user failed.
AccountManagerClient_LoginComplete result: … , user: …
TryRefreshTokenIfNeed  /  Refresh token  /  Refresh token failed.
RzActionSvc
```

Сценарий: `LoginAsync` → `AccountManagerClient.StartLogin` (команда 1) → ожидание
события `LoginComplete` с таймаутом → `GetCurrentUser`. Имя службы Windows, которую
приложение ищет, — **`RzActionSvc`**; исполняемый файл GUI —
`Razer\Razer Services\Razer Central\Razer Central.exe`.

Там же — генератор User-Agent для запросов к API:

```
GenerateUserAgent →  "RazerAxon/" + версия + " (Windows NT " + версия_ОС + "; Win64)"
запасной вариант:    "RazerAxon/1.0"
```

### 1.7. Мост, через который окно входа отдаёт токен

Страница `id.razer.com` рассчитана на нативный хост и общается с ним через два
глобала, которые хост обязан объявить **до** загрузки страницы:

```js
window.callbackObjforjs = { onEvent: function(action, payload, callback) { … } };
window.callJSFromClient  = function(action, data) { … };
```

Хост отвечает на `SET_WEBAPP_READY`, `GET_LANGUAGE`, `GET_THEME`, `GET_LOGIN_STATUS`,
`GET_MACHINE_ID_INFO`, `IS_WINDOW_VISIBLE`, а по завершении входа страница присылает
`SET_LOGIN_SUCCESS_FROM_WEB` с JSON-строкой `WebAppTokenInfo`. Это и есть весь
«протокол входа» — ни OAuth-редиректов, ни PKCE.

## 2. Что именно ломается под Wine

### Замер 1 — чистый префикс, Axon без Razer Central

Условия: `~/.wine-axon-auth`, wine-11.15, свежий `wineboot --init`, установка ровно по
рецепту из `установка_под_wine_2_9_1_0.md` (Inno-setup напрямую, тихий режим).
Установка снова прошла без единой правки префикса: 17:04:33 → 17:08:43, 373 файла,
WebView2 подтянулся сам (892 МБ в `Program Files (x86)/Microsoft`).

Запуск `RazerAxon.exe` — и вот весь его лог за четыре минуты:

```
17:17:17 |INFO| Program.cs:Main           App start************************************
17:17:17 |INFO| Program.cs:Main           startup args = -wrongaccess,isAdmin:True,userName:alexander,version:2.9.1.0
17:17:17 |INFO| Program.cs:TryLoginAsync  Start userLogin
17:17:47 |WARN| UserManager.cs:RegisterForUpdateAsync   register update failed.
         System.IO.IOException: Could not establish the connection.
          ---> System.TimeoutException: The operation has timed out.
            at Razer.ServiceClientBase.RazerClientBase.Connect(TimeSpan timeout)
            at Razer.Updater.UpdateClient.RegisterForUpdates(ProductDetails details)
17:18:17 |WARN| UserManager.cs:RegisterForUpdateAsync   Check update failed.   (та же трасса)
```

Дальше — **тишина**. Состояние на 17:21 (четыре минуты после старта):

| Что проверялось | Результат |
|---|---|
| окна (`wmctrl -l`) | ни одного окна Axon |
| процессы | жив только `RazerAxon.exe -wrongaccess`, `msedgewebview2.exe` не запускался |
| сеть (`ss -tnp state established`) | **ноль установленных соединений** |
| DNS (`resolvectl monitor`) | ни одного запроса от префикса |

⭐ **Вывод замера: без Razer Central приложение не доходит даже до экрана входа.**
Оно не «показывает форму и не пускает» — оно вообще не открывает окно, потому что
`TryLoginAsync` уходит в локальный IPC, которого нет, и не возвращается. Ни одного
байта в сеть при этом не уходит, так что списывать симптом на сеть, блокировки или
регион нельзя.

Это важное уточнение к прежней формулировке «упирается в отсутствие Razer Central»:
последствие не «нет обновлений», а **нет интерфейса вообще**.

### Замер 2 — ставим Razer Central: экран входа **достигнут**

Razer Central — .NET Framework, поэтому сначала `winetricks -q -f dotnet48`. Пара
уточнений к прежним заметкам, обе получены замером:

* `winetricks` **сам вернул префиксу win10** после установки (`Executing wine winecfg -v win10`,
  в реестре снова `CurrentBuild = 19045`). Прежняя формулировка «dotnet48 сбрасывает
  версию на win7 и надо чинить руками» для wine-11.15 + текущего winetricks
  **неверна** — версия восстанавливается.
* Ловушка `wineserver -w` из журнала установки подтвердилась дважды. ⚠️ И вот важное
  дополнение: **резидентных `MicrosoftEdgeUpdate.exe /c` в системе может быть
  несколько — по одному на каждый префикс.** Снимать надо строго свой, определяя
  владельца по окружению процесса:

  ```bash
  for p in $(pgrep -f MicrosoftEdgeUpdate); do
      echo "$p $(tr '\0' '\n' < /proc/$p/environ | grep ^WINEPREFIX=)"
  done
  ```

Дальше установка самого Razer Central:

```bash
wine ~/Загрузки/axon-installer-2026-08-10/RazerCentral_v7.23.0.1220.exe /silent
```

⭐ **Razer Central 7.23.0.1220 под Wine ставится.** Раньше журнал останавливался на
окне «Technology Required»; с настоящим .NET Framework 4.8 оно не появляется.
Доказательства:

```
C:\Program Files (x86)\Razer\Razer Services\Razer Central\      294 МБ
wine sc query RzActionSvc
    SERVICE_NAME: RzActionSvc
    STATE       : 4  RUNNING
```

Запускаем Axon снова — и цепочка идёт дальше:

```
19:45:46 Program.cs:Main          App start
19:45:47 Program.cs:TryLoginAsync Start userLogin
        ↓ (named pipe {CD7C71F0-…} → AccountManager.StartLogin)
19:45:52 WebAppViewModel   WebApp Address: https://id.razer.com/
19:45:54 ViewManager       ShowLoginWindow with center:True
19:45:54 ViewManager       Showing login window finished.
```

То есть **`StartLogin` доходит по IPC, Razer Central поднимает своё окно и грузит в
него `https://id.razer.com/`.** Окно появляется в списке окон (`Razer Central`,
1038×640).

### Замер 3 — почему окно входа сначала белое, и чем это лечится

Первый показ окна: **сплошной белый прямоугольник** (снимок весил 468 байт — одна
заливка). Причина видна в логе CEF
(`C:\ProgramData\Razer\Razer Central\Logs\cef_alexander.log`):

```
ERROR:network_change_notifier_win.cc(222)  WSALookupServiceBegin failed with: 0
ERROR:angle_platform_impl.cc(43)  ANGLE Display::initialize error 0: Internal Vulkan error (-3)
ERROR:gl_display.cc(917)          eglInitialize SwANGLE failed with error EGL_NOT_INITIALIZED
ERROR:gl_initializer_win.cc(133)  GLDisplayEGL::Initialize failed.
ERROR:viz_main_impl.cc(186)       Exiting GPU process due to errors during initialization
ERROR:gpu_init.cc(523)            Passthrough is not supported, GL is disabled, ANGLE is
ERROR:address_sorter_win.cc(108)  SIO_ADDRESS_LIST_SORT failed 0
```

и в логе самого Central:

```
DEBUG WebAppManager  Error, CefBrowser.IsWebAppReady: False, message: SET_LANGUAGE
```

Разбор процессов дал точную улику: подпроцессов CEF было **шесть — и ни одного
рендерера**:

```
2 × --type=gpu-process
4 × --type=utility
0 × --type=renderer      ← страница физически некому рисовать
```

⭐ **Дело не в GPU, а в песочнице Chromium: под Wine рендерер не стартует.** Проверка —
перезапуск GUI Razer Central с флагами Chromium:

```bash
cd "$WINEPREFIX/drive_c/Program Files (x86)/Razer/Razer Services/Razer Central"
wine "Razer Central.exe" /Client --no-sandbox --disable-gpu \
     --disable-gpu-compositing --disable-features=RendererCodeIntegrity
```

Результат — рендереры появились, и **экран входа Razer ID отрисовался полностью**:

```
2 × --type=renderer     ← появились
```

Снимок-доказательство: `~/Изображения/Screenshots/axon-2910-окно-входа-razer-central.png`
(1038×640). На экране, по-русски (Central сам выставил язык `Russian`): логотип Razer,
кнопки **ВХОД**, **РЕГИСТРАЦИЯ**, **ПРОДОЛЖИТЬ В КАЧЕСТВЕ ГОСТЯ** и вход через Apple,
Facebook, Google, Twitch, WeChat, Discord.

⚠️ Это **другой** дефект, чем известный WebView2/DirectComposition: Razer Central
рисует не на WebView2, а на **CefSharp** (свой Chromium). Прежняя формулировка README
«GUI Razer Central не отображается под Wine из-за ограничений WPF-рендеринга»
неточна — WPF там только рамка окна, содержимое рисует CEF, и лечится это
`--no-sandbox`.

### Замер 4 — гостевой вход проходит целиком

Нажатие **«ПРОДОЛЖИТЬ В КАЧЕСТВЕ ГОСТЯ»** (единственный путь, доступный без чужих
учётных данных):

1. окно Razer Central закрылось само;
2. Axon перезапустил себя с ключом `-showui`;
3. поднялись **шесть процессов `msedgewebview2.exe`**;
4. появились окна `RazerAxonHostWindow` и `Razer Axon`;
5. в логе пошла работа веб-слоя:

```
19:50:58 UserManagerHostObejct.cs:GetUserProfile   UserManagerHostObejct GetUserProfile called
19:51:00 UserManagerHostObejct.cs:PrintLog         UI Log:UI log- showBoarding true!
19:51:01 KinesisClient.cs:SendDataAsync            Send kinesis data: …|Settings|WallpaperPlay|…|Reason:AppStart
```

⭐ **Вывод: под Wine работает весь путь входа — IPC, окно Razer ID, выдача учётки,
запуск витрины.** Ни одной принципиальной поломки на маршруте авторизации не осталось;
всё, что мешало, — два флага Chromium.

Что осталось несовершенным: главное окно Axon рисуется лишь частично (тёмный фон и
логотип «AXON» в углу) — это **уже известная беда WebView2/DirectComposition**, стадия
отрисовки, а не входа. В этом заходе видно, почему обход не сработал: переменная
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` **до браузера не дошла** — в командной строке
`msedgewebview2.exe` наших флагов нет:

```
msedgewebview2.exe --embedded-browser-webview=1 --webview-exe-name=RazerAxon.exe
   --user-data-dir=…\UICache\2.9.1.0\EBWebView --noerrdialogs
   --embedded-browser-webview-dpi-awareness=2 --edge-webview-host-pid=928 …
```

Значит Axon задаёт `AdditionalBrowserArguments` в коде и перекрывает переменную
окружения. Вывод для порта: **флаги WebView2 надо доставлять не через окружение**
(например, `AppDefaults` + `--no-sandbox` через другой механизм), либо патчем.

### Про WebView2 и чёрное окно

Известный дефект (`DCompositionCreateDevice` → `E_NOTIMPL`, разобран в
`axon_installer_wine_diagnosis_2026_05_31.md`) в этом заходе **проверить не удалось**:
до запуска WebView2 дело не дошло. Фикс (`Version=win7` персонально для
`msedgewebview2.exe` при win10 у остального префикса) в префикс внесён заранее и
подтверждён в реестре:

```
[Software\Wine\AppDefaults\msedgewebview2.exe]
"Version"="win7"
```

но он лечит другую стадию — отрисовку уже открытого окна, а не вход.

**Замер офлайн-установки.** Отдельный префикс `~/.wine-axon-offline`, вся установка

Длится дольше обычного (5,5 мин против 4) — лишнее время уходит на попытки Edge Update
достучаться до Microsoft. Именно отсюда прежний симптом «поставилось, но окно пустое».

Замер живьём (соединения префикса `~/.wine-axon-auth`, отобраны по PID его

Он остаётся в префиксе после установки навсегда, сам себя перезапускает и ходит к

### 4.3. Что Razer заранее положил в кеш

⭐ Находка захода: **установщик кладёт готовый кеш Service Worker**, а Razer Central —
готовый `WebAppCache`. Из лога установки Inno:

```
Dest filename: C:\users\…\AppData\Local\Razer\RazerAxon\UICache\2.9.1.0\
               EBWebView\Default\Service Worker\CacheStorage\2453e6f6…\index.txt
```

Внутри `index.txt` — имя кеша и его origin:

```
cache-axon-static      https://axon-api.razer.com/
```

Файлы датированы 27.07.2026 (дата сборки), то есть это **предзаполненная офлайн-копия
оболочки витрины**, а не результат работы пользователя. Аналогично Razer Central при
старте копирует `C:\ProgramData\Razer\Razer Central\WebAppCache` →
`…\AppData\Local\Razer\Razer Central\WebAppCache`.

Смысл понятен: первый запуск не должен выглядеть пустым, пока грузится сеть. Но
**полноценной офлайн-работы это не даёт** — каталог обоев, миниатюры и вход всё равно
сетевые.

### 4.4. Можно ли жить офлайн — короткий ответ

| Сценарий | Результат |
|---|---|
| установка Axon без сети | **проходит**, но WebView2 не ставится → интерфейса не будет |
| установка «под ключ» без сети | нет: нужны WebView2 (~190 МБ) и Razer Central (121 МБ) |
| первый вход без сети | **невозможен**: окно входа — это `id.razer.com` |
| повторный запуск без сети после гостевого входа | **упирается в то же окно входа** (замер ниже) |
| уже скачанные обои | играются локально (плеер сети не требует) |

**Замер запуска без сети на полностью настроенном префиксе.** Тот же
`~/.wine-axon-auth`, где гостевой вход уже прошёл; префикс погашен и запущен заново
целиком внутри изолированного сетевого пространства:

```bash
wineserver -k
unshare -rn bash -c 'ip link set lo up; wine RazerAxon.exe'
```

Через 100 секунд:

```
процессы:  RazerAxon.exe -wrongaccess
           RazerCentralService.exe
           Razer Central.exe /Client + 3 × CefSharp.BrowserSubprocess.exe
           msedgewebview2.exe — НИ ОДНОГО
окна:      «Razer Central»  (новое окно входа)
```

⭐ **Гостевая сессия перезапуск не пережила**: Razer Central снова поднял окно входа.
А само окно без сети пустое — рамка Razer рисуется (это WPF), содержимое не грузится,
потому что `id.razer.com` недостижим. Снимок:
`~/Изображения/Screenshots/axon-2910-вход-без-сети.png`.

Практический вывод: **предзаполненный кеш спасает только оболочку витрины, но не
вход.** Пока Razer Central не отдаст учётку, Axon даже не запускает WebView2 — то
есть офлайн приложение бесполезно на любом заходе, а не только на первом.

Всё остальное (реклама, телеметрия, обновления, zVault) можно резать без потери
основной функции.

## 5. Что нужно от человека

Замеры доведены до предела, доступного без чужой учётной записи:

* **гостевой вход пройден целиком и работает** — этого хватило, чтобы доказать, что
  под Wine исправен весь маршрут: IPC → окно Razer ID → выдача учётки → запуск витрины;
* **настоящий вход по Razer ID не проверялся** — учётной записи Razer у исполнителя
  нет, выдумывать её и регистрировать новую нельзя.

Чтобы закрыть остаток, от Wehrwolfmann нужно ровно одно действие:

1. запустить приложение по рецепту ниже, дождаться окна Razer ID;
2. нажать **«ВХОД»** и войти своей учётной записью Razer (пароль вводится в окне
   самого Razer, никуда не передаётся и в журнал не попадает);
3. сказать, что получилось: открылась ли витрина с его именем и аватаром.

```bash
export WINEPREFIX="$HOME/.wine-axon-auth"

# 1. GUI Razer Central — обязательно с --no-sandbox, иначе окно белое
cd "$WINEPREFIX/drive_c/Program Files (x86)/Razer/Razer Services/Razer Central"
wine "Razer Central.exe" /Client --no-sandbox --disable-gpu &

# 2. само приложение
cd "$WINEPREFIX/drive_c/Program Files (x86)/Razer/Razer Axon"
wine RazerAxon.exe
```

Что именно даст живой вход и чего нельзя получить гостем:

| Вопрос | Закрывается только настоящим входом |
|---|---|
| проходит ли двухфакторная проверка (`OtpRequired` в `LoginResult`) под Wine | да |
| работает ли «оставаться в системе» (клиентский сертификат Razer Central) | да |
| переживает ли сессия перезапуск префикса | да |
| отдаёт ли `oauth2.razer.com/services/code_sso` код и открывается ли профиль | да |
| работает ли вход через соцсети (`ConnectToAccount`, Google/Twitch/Discord) | да |
| видны ли избранное, плейлисты и покупки | да |

⛔ Пароль и токен передавать в переписку не нужно: всё, что требуется, — сам факт
«вошло / не вошло» и, если не вошло, строки из
`C:\ProgramData\Razer\Razer Central\Logs\Razer Central_<пользователь>.log`.

## 6. Дефекты Wine, найденные на маршруте входа

Правки для игр и Windows-программ подаются в **Wine**, не в Proton. Здесь — только
то, что подтверждено замером на этом маршруте (дефекты этапа установки — в
`установка_под_wine_2_9_1_0.md`).

### А1. Рендерер Chromium не стартует без `--no-sandbox` — **главная находка захода**

Симптом: CefSharp поднимает `gpu-process` и `utility`, но **ни одного
`--type=renderer`**; окно остаётся белым, приложение считает страницу незагруженной
(`CefBrowser.IsWebAppReady: False`). С `--no-sandbox` рендереры появляются и страница
рисуется полностью.

Ценность для апстрима высокая: это бьёт **по любому приложению на CEF/Electron под
Wine**, а не только по Razer. Перед подачей нужно уточнить, на чём именно спотыкается
запуск дочернего процесса в песочнице (прогон с `WINEDEBUG=+process,+seh` и снятие
кода выхода рендерера) — сейчас зафиксирован только факт.

### А2. `WSALookupServiceBegin` не работает — Chromium не видит смену сети

```
ERROR:network_change_notifier_win.cc(222)  WSALookupServiceBegin failed with: 0
```

Повторяется при каждом старте CEF. Chromium использует это для слежения за
подключениями; под Wine уведомления о сети не приходят. На вход не повлияло, но это
честный пробел в `ws2_32`.

### А3. `SIO_ADDRESS_LIST_SORT` не поддержан

```
ERROR:address_sorter_win.cc(108)  SIO_ADDRESS_LIST_SORT failed 0
```

Chromium сортирует адреса (RFC 3484) через этот ioctl; под Wine он не отрабатывает,
и порядок IPv4/IPv6 остаётся произвольным. Малый приоритет, но починка тривиальна.

### А4. ANGLE не инициализируется даже в программном режиме

```
ANGLE Display::initialize error 0: Internal Vulkan error (-3)
eglInitialize SwANGLE failed with error EGL_NOT_INITIALIZED
GLDisplayEGL::Initialize failed → Exiting GPU process
```

Падает не только аппаратный путь, но и программный **SwANGLE**. Родственно известной
беде WebView2 с DirectComposition, но проявляется раньше и в другом месте. На вход не
влияет (после `--no-sandbox` страница рисуется и без GPU).

### А5. Не дефект Wine: `AdditionalBrowserArguments` перекрывает окружение

Переменная `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` до браузера **не доходит** — Axon
задаёт аргументы WebView2 в коде. Это особенность приложения, а не Wine; для порта
означает, что флаги WebView2 надо доставлять другим способом.
