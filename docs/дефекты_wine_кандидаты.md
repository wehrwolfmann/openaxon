## 1. DirectComposition / WebView2 — дубликат, но комментарий ценный

Самый весомый кандидат оказался уже заведён, причём дважды:

* **bug 58921** «WebView2 does not work with Windows version setting 8.1 or newer»
  (UNCONFIRMED, заведён 2025-11-04, к нему приклеены дубликаты 59370 и 59431).
  В нулевом комментарии — тот же обход, что нашли мы: per-app `Version=win8`
  для `msedgewebview2.exe`.
* **bug 55432** «PlanetSide 2 launcher is completely white (needs
  dcomp.dll.DCompositionCreateDevice implementation)» (NEW с 2023-08, компонент `dcomp`).

**В апстриме не починено.** `dlls/dcomp/device.c` в master — 47 строк: все три точки
входа печатают FIXME и возвращают `E_NOTIMPL`; в `dcomp.spec` реализованы только они,
остальные 14 экспортов — `stub`. В wine-staging есть отдельный патчсет
`dcomp-DCompositionCreateDevice2` (он же дал регрессию — bug 59918), в апстриме идёт
MR 10567; ванильный Wine остаётся стабом.

Замер на 11.15 своим воспроизведением `repro/dcomp_min.c` (~90 строк, никакого
WebView2 и Razer не нужно — программа делает ровно тот вызов, что делает Chromium
при заявленной Windows ≥ 8.1):

```
reported Windows version: 10.0 build 19045
D3D11CreateDevice hr=0x00000000 feature_level=0xb000
QI IDXGIDevice hr=0x00000000
DCompositionCreateDevice(IDCompositionDevice)         hr=0x80004001
DCompositionCreateDevice2(IDCompositionDevice2)       hr=0x80004001
DCompositionCreateDevice3(IDCompositionDesktopDevice) hr=0x80004001
```

D3D11-устройство и его `IDXGIDevice` создаются нормально — падает только создание
DirectComposition-устройства. Это и есть та единственная точка, из-за которой
viz-процесс Chromium бьёт CHECK и кадр не доходит до окна.

Ценность нашего вклада: подтверждение на 11.15, третье затронутое приложение
(Razer Axon 2.9.1.0 — весь интерфейс на WebView2, рантайм 151.0.4129.78), и главное —
воспроизведение без 120-мегабайтного установщика, без Steam и без DXVK (прошлые
замеры в 55432 были с DXVK, за что репортёра отчитали).

Текст двух комментариев: `02-dcomp-webview2-ДУБЛИКАТ-комментарии.md`.

## 2. `riched20`: `\ctint`/`\cshade` разваливают таблицу цветов — НОВЫЙ БАГ

Это единственный кандидат, который идёт наверх как самостоятельный баг.

Причина найдена в `dlls/riched20/reader.c`. Таблица ключевых слов знает ровно три
слова таблицы цветов:

```c
{ rtfColorName, rtfRed,   "red",   0 },
{ rtfColorName, rtfGreen, "green", 0 },
{ rtfColorName, rtfBlue,  "blue",  0 },
```

`\ctint`, `\cshade` и слова тем оформления (`\cmaindarkone`, `\caccentone` …) —
законные по спецификации RTF внутри `\colortbl` — не опознаются. `ReadColorTbl()`
на них обрывает запись, печатает `err:richedit:ReadColorTbl malformed entry` и
начинает **новую** запись цвета со следующего токена. Одна исходная запись
превращается в три, все последующие `\cfN` уезжают по индексу, а поддельные записи
создаются со значением «цвет по умолчанию», из-за чего текст получает `CFE_AUTOCOLOR`
вместо своего цвета.

Замер (`repro/riched_colortbl.c` — три документа, по спецификации одинаковых,
читаем `EM_GETCHARFORMAT` после `EM_STREAMIN`):

```
expected for every line: crTextColor=0x0000ff (R=255 G=0 B=0)

A plain colortbl      crTextColor=0x0000ff (R=255 G=0 B=0)
B \ctint\cshade       crTextColor=0x007fff (R=255 G=127 B=0)  [CFE_AUTOCOLOR]
C Word theme colour   crTextColor=0x007fff (R=255 G=127 B=0)  [CFE_AUTOCOLOR]
```

Это не экзотика: так пишет Word 2007 и новее для любого документа с цветами темы,
и именно такой RTF кладут в лицензию установщики на Inno Setup — отсюда наши
шесть `malformed entry` при показе лицензии Razer.

Дубликата нет. Ближайшие соседи: **bug 20482** (2009, компонент richedit) — там тот же
`ReadColorTbl malformed entry`, но заведён на симптом конкретной программы
(«слишком высокий диалог Tunnelier») и причина за 17 лет не разобрана; **bug 44966** —
про `ReadStyleSheet`, другое место. Наш репорт даёт причину, минимальный пример и
готовый юнит-тест.

Текст: `01-riched20-colortbl-ctint-cshade.md`.

## 3. `shell32`: `IShellLinkW::QueryInterface` → `E_NOINTERFACE` — отпал

Прогон `RazerAxon.exe` с `WINEDEBUG=+shell` в своём префиксе показал, какие именно
IID запрашиваются и остаются без ответа:

| IID | Что это |
|---|---|
| `{ecc8691b-c1db-4dc0-855e-65f6c551af49}` | `INoMarshal` |
| `{94ea2b94-e9cc-49e0-c0ff-ee64ca8f5b90}` | `IAgileObject` |
| `{00000003-0000-0000-c000-000000000046}` | `IMarshal` |
| `{5c13e51c-4f32-4726-a3fd-f3edd63da3a0}` | недокументированный интерфейс, который среда COM опрашивает сразу после `CoCreateInstance` |

Все четыре — стандартные «прощупывания» среды COM сразу после создания объекта,
и `E_NOINTERFACE` на них — **правильный** ответ: объект ярлыка не является agile и
маршалится стандартным способом. Дефекта поведения нет; сразу после этих четырёх
запросов `IShellLinkW` и `IPersistFile` отдаются нормально, и `SetPath` отрабатывает.

Остаётся косметика: Wine печатает неудачный `QueryInterface` уровнем `ERR`
(`dlls/shell32/shelllink.c`, конец `IShellLinkW_fnQueryInterface`), хотя по общей
практике Wine неудачный QI — это `WARN`/`TRACE`. Из-за этого в логе любой программы
висят четыре красные строки на ровном месте. Годится как однострочный патч в MR,
но не как баг-репорт — репорт про уровень логирования закроют.

## 4. `riched20`: `ReadStyleSheet skipping optional destination` — отложен

Сообщение печатается, когда запись таблицы стилей начинается с `\*` (`{\*\cs10 …}`) —
Wine пропускает такую запись целиком. Bug 44966 (REOPENED, richedit) уже висит на
этом же месте. Видимой поломки на нашем сценарии измерить не удалось: текст лицензии
показывается, стили в реализации Wine почти не используются. Без измеренного
пользовательского симптома не подаём — иначе получится второй 44966.

## 5. `combase`: нет WinRT-класса телеметрии — отпал

`RoGetActivationFactory` не находит
`Windows.System.Diagnostics.Telemetry.PlatformTelemetryClient` (запрашивает Edge
Update изнутри). Класс телеметрии Microsoft — реализовывать его в Wine незачем,
отказ и есть правильное поведение, установка от этого не страдает. Подавать нечего.
Похожие «нет WinRT-класса» баги в Bugzilla есть (например 56914 про
`Windows.Data.Json.JsonObject`), но там класс реально нужен приложению.

## 6. Стабы по дороге — отпали

`WerRegisterCustomMetadata`, `clusapi:ClusterEnum`, `advapi:DecryptFileW`,
`nls:get_dummy_preferred_ui_language`, `msi:internal_ui_handler` — все `fixme`,
ни один ничего не сломал. Это штатные метки незавершённых мест, а не дефекты;
репорт «видел fixme» закроют.

## 7. `wineserver -w` и резидентный `MicrosoftEdgeUpdate.exe` — не в Wine

Установка WebView2 оставляет в префиксе вечный `MicrosoftEdgeUpdate.exe /c`, после
чего любой verb winetricks встаёт на `wineserver -w` (замер: процесс жив 1010 с,
снятие ровно этого PID разблокировало установку немедленно). Wine ведёт себя
правильно — он честно ждёт последний процесс префикса. Место для правки — winetricks
(снимать резидент Edge Update перед `wineserver -w`) и/или строка в AppDB.

## 8. Меню значка в трее — дефекта Wine нет (замер 2026-08-14)

Разбирали жалобу «правый щелчок по значку в трее не даёт ничего» (заход 17
в `установка_под_wine_2_9_1_0.md`). Проверялось на wine-11.15, Plasma 6.7.4
на Wayland, значки проводит `xembedsniproxy`.

**Трей Wine исправен.** `WINEDEBUG=+systray` показывает, что подложный щелчок от
`xembedsniproxy` доходит и передаётся владельцу целиком — `WM_RBUTTONDOWN`,
`WM_RBUTTONUP`, `WM_CONTEXTMENU`; окно меню создаётся и позиционируется правильно
(157×186, с переворотом вверх над нижней панелью). Контрольная программа
`repro/tray_min.c` (чистый Win32, `Shell_NotifyIcon` + `TrackPopupMenu`) в том же
трее рисует меню полностью.

Чёрным оставалось содержимое, потому что меню значка у Razer Central рисует WPF
(`Hardcodet.Wpf.TaskbarNotification`), а тот по умолчанию идёт через Direct3D 9.
Ключ `Avalon.Graphics\DisableHWAcceleration` меню чинит.

⚠️ **Вывод «дефекта Wine нет» оказался неверным — см. раздел 9.** Замер 2026-08-14
показал, что за чёрным меню стоит настоящий дефект Wine в `winex11.drv`, а ключ
реестра лишь уводит WPF с ломающегося пути. Раздел оставлен как есть, чтобы была
видна история разбора.

**Побочное наблюдение, требующее замера на настоящей Windows.**
`programs/explorer/systray.c` шлёт `WM_CONTEXTMENU` при любой версии значка больше
нуля:

```c
if (icon->version > 0)
{
    if (msg == WM_LBUTTONUP) notify_owner( icon, NIN_SELECT, lparam );
    if (msg == WM_RBUTTONUP) notify_owner( icon, WM_CONTEXTMENU, lparam );
}
```

По документации Microsoft `WM_CONTEXTMENU` относится к `NOTIFYICON_VERSION_4`,
а не к версии 3. Видимое следствие у нас замерено: на один правый щелчок Razer Central
открывает меню **дважды** — в списке окон друг за другом появляются два окна меню
(`0x2600012`, затем `0x2600014`), первое тут же уничтожается вторым. Вреда это не
наносит, итоговое меню работает.

Подавать **не** будем: по нашему же правилу репорт без собственного замера не идёт,
а поведение настоящей Windows здесь проверить не на чем. Если появится машина
с Windows — замерить, какие сообщения приходят при `NIM_SETVERSION` = 3, и тогда
решать. Воспроизведение уже готово: `repro/tray_min.c` умеет и версию 3, и версию 4,
и печатает каждое пришедшее сообщение.

## 9. Русские подписи квадратиками: у WPF под Wine нет ни одного запасного шрифта — НОВЫЙ БАГ (замер 2026-08-14)

Жалоба: в контекстном меню значка Razer Central в трее латиница читается, а русские
пункты — ряды пустых прямоугольников (снимок `~/Изображения/Screenshots/axon-трей-меню-работает.png`).

### Чем рисуется текст

Razer Central несёт **свой** шрифт. Внутри `Razer Central.exe` лежат 23 шрифтовых
файла: десять начертаний фирменного **RazerF5** (SIL OFL, переделан из Titillium)
и тринадцать начертаний Roboto. Ссылки на них в ресурсах WPF —
`…/Fonts/#RazerF5`, `…/Fonts/#RazerF5 Light`, `…/Fonts/#Roboto` (`UICommon.dll`).

Замер покрытия (разбор таблиц `cmap` вынутых файлов):

| Шрифт | Знаков | Кириллица |
|---|---|---|
| RazerF5 (все 10 начертаний) | 229-230 | **0** |
| Roboto (13 начертаний) | 896 | 255 |

То есть у Roboto кириллица есть, а у RazerF5 её нет вовсе. Меню рисуется RazerF5 —
иначе русские пункты читались бы.

### Где теряется кириллица

WPF **не пользуется** ни разметкой DirectWrite, ни его подбором запасного шрифта
(это же говорит мейнтейнер dwrite в bug 50021). У него своя таблица —
`GlobalUserInterface.CompositeFont`, который ставится вместе с .NET. Таблица
расписана именами системных шрифтов Windows. За полосу `U+0000-U+052F` (латиница,
греческий, **кириллица**) в разделе для Windows 10 отвечает одна строка:

```
<FontFamilyMap Unicode = "0000-052F, 0590-05FF, …"
               Target  = "Segoe UI, Segoe UI Symbol, Ebrima" />
```

Ни одного из трёх шрифтов в префиксе Wine нет и быть не может — они несвободные.
Всего в разделе Windows 10 RS5 названо **44** запасных семейства, из них в Wine
находится **одно** (Tahoma, и та в цепочке для кириллицы не упомянута), а 43 не
находятся. Для кириллицы цепочка пуста целиком, поэтому WPF не рисует ничего,
а меню показывает `.notdef`.

Обычная программа WPF беды не замечает: её шрифт по умолчанию приходит из
`SystemParametersInfo`, а Wine отвечает «Tahoma», в которой кириллица есть.
Страдают ровно те, кто принёс свой фирменный шрифт, — а фирменные шрифты почти
всегда только латинские.

### Из трёх версий верна вторая

* **(а) подмена не срабатывает** — нет: механизм цел, он упирается в пустоту.
* **(б) подставлять нечего** — **да**, но не так, как думали в прошлый заход:
  кириллических шрифтов в префиксе полно (DejaVu, Noto, Liberation — WPF видит 319
  семейств). Не хватает шрифтов **именно с теми именами**, которые записаны в
  таблице Microsoft. Поэтому подкладывание `tahoma.ttf` и `Roboto-Regular.ttf`
  в прошлый заход и не помогло: имя не то. Вывод «WPF берёт шрифт из ресурсов
  Razer» оказался верным лишь наполовину — шрифт действительно оттуда, но
  причина квадратиков не в этом, а в оборванной цепочке запасных.
* **(в) дефект Wine в подборе** — частично: сам подбор не ломается, но Wine
  **не даёт** ни одного шрифта под нужными именами, хотя механизм для этого
  у него есть и не задействован (см. ниже).

### Замер, разделяющий слои

`repro/wpf_fonts.cs` — зонд на WPF, собирается тем самым `csc.exe`, что уже лежит
в префиксе, SDK не нужен. Для каждого имени печатает, находится ли семейство,
покрывает ли оно латиницу и кириллицу, и границы контуров, которые реально выдал
`FormattedText.BuildGeometry`. Пустые границы = не нарисовано ничего.

```
family "RazerF5"   resolved=True latin=True cyrillic=False
    latin     outline=53,7x14,8
    cyrillic  outline=EMPTY (nothing drawn)
family "Tahoma"    resolved=True latin=True cyrillic=True
    cyrillic  outline=75,6x15,0
family "Segoe UI"  resolved=False
```

`repro/gdi_cyrillic.c` — то же самое через обычный GDI, для сравнения слоёв:

```
face "Segoe UI"  cyrillic missing_glyphs=0/9 painted=637  (GetTextFace Liberation Sans)
face "RazerF5"   cyrillic missing_glyphs=9/9 painted=653  (GetTextFace RazerF5)
```

Win32 кириллицу рисует: попросили «Segoe UI» — Wine молча подставил Liberation Sans.
Эта уступчивость живёт на уровне **выбора** шрифта и не видна тому, кто сперва
спрашивает «а есть ли такое семейство». WPF спрашивает именно так, получает «нет»,
и вместе с ответом умирает вся его таблица запасных.

Побочно замерено: если не находится и **запрошенное** семейство, WPF под Wine не
откатывается на что-либо по умолчанию, а молча роняет процесс внутри вёрстки текста
(`wine wpf_fonts.exe "Segoe UI"` — вывод обрывается, ни исключения, ни сообщения).
Похоже на тот же корень, что в bug 50021 (PS Remote Play, срабатывание проверки
в `TypefaceMap.MapUnresolvedCharacters`, «установка corefonts меняет поведение»).

### Чем лечится

У Wine **уже есть** нужный механизм, просто без записей по умолчанию:
`HKCU\Software\Wine\Fonts\Replacements` — его читают и `win32u/font.c`
(`load_gdi_font_replacements`), и `dwrite/font.c`. Он показывает имеющийся шрифт под
дополнительным именем и сам отступает, если настоящий шрифт с таким именем появится.
`REG_MULTI_SZ` поддержан, берётся первый найденный, поэтому одна запись годится для
любого дистрибутива.

Замер на префиксе, файлы `*.CompositeFont` не тронуты:

```
до     family "RazerF5"  cyrillic outline=EMPTY (nothing drawn)
после  family "RazerF5"  cyrillic outline=80,8x16,0   (метрики Noto Sans)
```

Снимки `repro/wpf_fonts_before.png` и `repro/wpf_fonts_after.png`.

Перекрёстная проверка: если вместо реестра дописать существующее семейство в каждый
`Target` внутри `*.CompositeFont`, чинится тоже (3684 правки в 16 файлах). Реестр
лучше — не трогаем файлы, принадлежащие .NET.

В `scripts/установить-axon.sh` это шаг 9 (`setup_fonts`): три записи для
`Segoe UI`, `Segoe UI Symbol` и `Ebrima` со списком
`Noto Sans|DejaVu Sans|Liberation Sans|Arial|Tahoma`. Tahoma в конце — надёжный пол:
она входит в сам Wine, латиницу с кириллицей закрывает.

## 9. ⭐ Слоёное окно + Direct3D = чёрный прямоугольник (замер 2026-08-14)

Возврат к разделу 8: вопрос «почему аппаратный путь WPF под Wine даёт чёрное окно»
разобран до конца, и **дефект Wine есть**. Он не в WPF, не в `d3d9` и не в трее.

**Где ломается.** Всё, что делает WPF, отрабатывает правильно:

* `Direct3DCreate9Ex`, `CreateDeviceEx`, `CreateAdditionalSwapChain`,
  `GetRenderTargetData`, `LockRect` — все возвращают `S_OK`, ни одного
  `E_NOTIMPL`/`D3DERR_*` в трассировке `+d3d9,+d3d` нет;
* `RenderCapability.Tier` = `0x00020000` (второй уровень, аппаратный) —
  WPF под Wine честно считает, что видеокарта есть, и не откатывается сам;
* прочитанные назад пиксели **верные**, `UpdateLayeredWindow` возвращает `TRUE`.

Окно всё равно чёрное, потому что свопчейн навешивает на окно **клиентское
X-окно** — непрозрачного ребёнка ровно по размеру окна, который закрывает собой
всё, что нарисовал `UpdateLayeredWindow`:

```
xwininfo: Window id: 0x5c00006 "layered"
   Parent window id: 0x350 (the root window)
      1 child:
      0x5a00036 (has no name): ()  300x120+0+0  +80+80
```

**Что именно виновато.** В `dlls/winex11.drv/init.c` есть готовый механизм: когда
окну нужна композиция, клиентское окно отцепляется и вывод перенаправляется через
XComposite (`client_surface_update_offscreen`). Решает это `needs_offscreen_rendering()`,
и в её списке три случая — масштаб DPI, дочернее окно, окно с детьми. **Слоёного
окна там нет**, хотя его содержимое как раз собирается композицией.

**Проверено правкой.** Одна строка

```c
if (NtUserGetWindowLongW( hwnd, GWL_EXSTYLE ) & WS_EX_LAYERED) return TRUE;
```

переворачивает замер: пиксель в центре окна был `rgb(0,0,0)`, стал `rgb(255,0,0)`.
На WPF-пробнике из четырёх окон в одной программе до правки чернели ровно два
прозрачных, после правки рисуются все четыре.

**Воспроизведения (без Razer и без учётной записи), в `repro/` рядом с отчётами:**

| Файл | Что делает |
|---|---|
| `d3d9_layered.c` | ~190 строк чистого Win32 + D3D9Ex: слоёное окно, `Clear` в красный, `GetRenderTargetData`, `UpdateLayeredWindow`; режимы `nod3d` и `plain` — контроли |
| `wpf_layered.cs` | то же на WPF: обычное окно / слоёное окно / всплывашка непрозрачная / всплывашка прозрачная; собирается штатным `csc.exe` из .NET 4.8 в префиксе |
| `winex11-layered-offscreen.patch` | проверенная однострочная правка |

**Область поражения шире Axon:** чернеет любое меню, подсказка и выпадающий список
любой программы на WPF, а также любое окно с `AllowsTransparency="True"`. Отсюда
и живучесть совета `DisableHWAcceleration` по форумам.
